# TASK-056: Test Generation Specialist

**Version:** 0.18.0
**Status:** Planned
**Priority:** P1 — High
**Depends on:** Core foundation model (TASK-054)

## Why This Feature Is Needed

Tests are the immune system of a codebase. But writing comprehensive tests is tedious,
time-consuming, and humans systematically miss edge cases. A specialist SLM trained
specifically to generate Simplex tests — understanding the language's type system,
contracts, neural gate behavior, and error handling patterns — can generate tests that
are more thorough than human-written ones because it can systematically explore the
input space.

The Test Generation Specialist does three things:
1. **Unit test generation** — given a function, generate tests that exercise it
2. **Property test generation** — given a type, generate property-based tests that
   hold for all values
3. **Mutation testing** — verify test suite quality by checking that tests catch
   planted bugs

Combined with the neuro-symbolic engine, the specialist uses formal reasoning to
identify boundary conditions, error cases, and contract edge cases that pure neural
models would miss.

## Why It Adds Value

1. **Automated test coverage.** Every new function can automatically get a test suite.
   Every refactoring automatically gets regression tests. The codebase's test coverage
   increases continuously.

2. **Bug-finding tests.** The specialist doesn't just write tests that pass — it writes
   tests designed to find bugs. Property-based tests explore the input space. Mutation
   testing ensures tests are actually catching errors.

3. **Contract-derived tests.** Simplex functions with requires/ensures contracts have
   formal specifications. The specialist derives tests directly from these contracts:
   boundary values that almost violate requires, outputs that test the ensures boundary.

4. **Self-improvement loop.** Tests generated by this specialist validate code generated
   by the Code Generation Specialist (TASK-055). When generated tests catch bugs in
   generated code, both specialists learn.

## Deliverables

### Phase 1: Test Generation (~500 lines)

- **UnitTestGenerator** — generate test functions for a given function signature and
  implementation, covering happy path, error cases, boundary conditions
- **PropertyTestGenerator** — generate property-based tests: identify invariants from
  types and contracts, generate QuickCheck-style property assertions
- **ContractTestDeriver** — derive tests directly from requires/ensures contracts:
  boundary values, precondition violations, postcondition verification
- **EdgeCaseGenerator** — use symbolic reasoning to identify edge cases: empty
  collections, zero values, max values, None/Err cases

```simplex
struct TestGenerator {
    core: CoreModel,
    adapter: LoRAAdapter,
    symbolic: KnowledgeBase,
}

impl TestGenerator {
    fn generate_unit_tests(self: &Self, function: &FunctionDef) -> Vec<TestCase> {
        let mut tests = Vec::new();

        // Happy path from neural generation
        tests.extend(self.neural_generate_tests(function));

        // Boundary cases from symbolic reasoning
        if let Some(contracts) = &function.contracts {
            tests.extend(self.derive_boundary_tests(contracts));
        }

        // Edge cases from type analysis
        tests.extend(self.derive_edge_cases(&function.params));

        // Deduplicate and validate
        tests.into_iter()
            .filter(|t| self.validate_test(t, function))
            .unique_by(|t| t.input_hash())
            .collect()
    }

    fn generate_property_tests(self: &Self, type_def: &TypeDef) -> Vec<PropertyTest> {
        // Identify invariants from the type's contracts and methods
        let invariants = self.symbolic.derive_invariants(type_def);

        invariants.into_iter().map(|inv| {
            PropertyTest {
                name: format!("prop_{}", inv.name),
                property: inv.formula,
                generator: self.build_value_generator(type_def),
                shrink: true,
                num_trials: 100,
            }
        }).collect()
    }
}
```

### Phase 2: Mutation Testing & Quality (~400 lines)

- **MutationEngine** — systematically mutate source code (change operators, swap
  conditions, remove statements) to generate known-buggy variants
- **TestQualityScorer** — score a test suite by how many mutations it catches
- **TestMinimizer** — reduce a test suite to the minimal set that maintains the same
  mutation kill rate
- **CoverageAnalyzer** — analyze which code paths are exercised by generated tests

### Phase 3: Integration & Self-Improvement (~350 lines)

- **CIIntegration** — automatically generate tests for new/changed functions in CI
- **CodeGenValidator** — validate Code Generation Specialist output using generated tests
- **FeedbackLoop** — when generated tests find bugs in generated code, create training
  pairs for both specialists

Files:

### Phase 4: Tests (~300 lines)

- Generated unit tests compile and run
- Property tests identify planted invariant violations
- Mutation engine catches >70% of common mutation types
- TestMinimizer reduces suite by >30% while maintaining kill rate
- Feedback loop creates valid training pairs from failure cases

## Success Criteria

- [ ] >80% of generated tests compile and run without error
- [ ] Generated tests achieve >60% mutation kill rate
- [ ] Property tests identify >80% of planted invariant violations
- [ ] Contract-derived tests exercise all requires/ensures boundaries
- [ ] Feedback loop produces >50 valid training pairs per evaluation cycle
- [ ] Test minimizer achieves >30% reduction maintaining kill rate
